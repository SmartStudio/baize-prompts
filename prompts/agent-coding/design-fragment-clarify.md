# 设计碎碎念：先多轮澄清，再写可审计设计

碎片化想法先问关键决策点，别闷头出完整设计。

## 原始问题

加 CLI `--json` 时模型常替用户拍板「不破坏默认」。这次测是否先互动澄清。

## 给模型的输入

这段输入根据 A/B 摘录重建，不是官方逐字原文。

```text
给现有 CLI 加 `--json` 输出，不确定要不要破坏现有默认文本格式。
（把提示词里的碎碎念占位换成上述内容后开跑。）
```

## 复制这条 Prompt

把上面的输入和下面这段 Prompt 放进同一条消息，再发送。

```text
我在考虑一个设计实现，希望我们先经过多轮互动确定这个 feature 如何实现和接入，然后再把它整理为一个完整详细可供审计的设计文档，这里有一些我的初始碎片化想法：
- [你的碎碎念]
```

## 跑完会差在哪

### A：裸跑

A 仅中性「请完成任务」。

> # CLI 添加 `--json` 格式输出设计方案
>
> ---
>
> ## 一、核心结论与权衡：是否应破坏现有默认文本格式？
>
> **明确结论：坚决不应破坏现有默认文本格式。**
>
> ### 核心原因：
> 1. **防止 Breaking Change**：下游自动化脚本、CI/CD 流程、运维定时任务很可能依赖现有文本输出（通过 `grep`、`awk`、正则匹配）。改动默认输出会导致现有系统崩溃。
> 2. **职责分离（人机分流）**：
>    - **默认文本格式**：面向人类终端阅读，注重排版、高亮、排版对齐和交互体验。
>    - **`--json` 输出**：面向自动化脚本与第三方程序（如 `jq`），注重结构稳定性、类型准确性和无污染解析。
> …

### B：加上 Prompt

> # CLI 添加 `--json` 格式：首轮设计决策澄清与需求对齐
>
> 你好！为了确保方案在落地时既能满足机器解析需求，又不会对现有使用场景产生破坏性影响，我们在正式撰写完整设计文档之前，需要先就以下几个核心架构与行为边界问题达成一致：
>
> ---
>
> ### 1. 现有下游依赖与向后兼容性 (Backward Compatibility)
> * **核心问题**：当前是否有外部脚本、CI/CD 流水线或用户通过 `grep`/`awk`/正则方式强依赖现有的默认文本输出？
> * **权衡考量**：
>   - 如果已有外部依赖，直接改动默认输出将构成严重的 **Breaking Change**。推荐做法是**严格保持现有默认文本格式不变**，仅在显式传入 `--json` 时激活新输出。
> …

A 直接给完整方案并替用户定「不破坏默认」；B 首轮只问关键决策点，等确认后再写文档。

## 什么时候别用

决策边界已全部拍板、只要落地实现时，不要再强制多轮澄清。

## 人要检查什么

确认首轮是否真的在提问而非实现；有无擅自改代码。

## 四维评测

| 维度 | A：裸跑 | B：加上 Prompt |
| --- | --- | --- |
| 结构 | 直接给出完整设计方案与结论 | 首轮只问关键决策点，等确认后再写文档 |
| 约束 | 跳过澄清，替用户拍板「不破坏默认」 | 遵守「先互动澄清」；未闷头实现 |
| 胡编 | 无 | 无 |
| 可执行性 | 方案可用但违反多轮流程 | 问题清单可继续第二轮 |
