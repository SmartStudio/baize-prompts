# 白泽 Prompt 出厂文档怎么写

一条 Prompt 值不值得复制，20 秒就该看明白：原来卡在哪，输入了什么，Prompt 是什么，跑完差在哪。

正文按这个顺序走：**原始问题 → 给模型的输入 → Prompt → A/B 结果 → 判断**。别从术语、分类和评测流程讲起。读者来这里是想马上试，不是来填实验报告。

## 先把问题和输入摆出来

开头直接写原始问题。谁在干什么，模型哪里写坏了，这条 Prompt 准备修哪一下。两三句够了。

下一节贴给模型的完整输入。读者不该猜测试条件，也不该翻到文末找原文。官方输入没留下，就明确写「这段输入根据 A/B 摘录重建，不是官方逐字原文」，然后贴出重建内容。能追溯不等于能冒充原文。

## 让人复制两次就能开跑

输入一个代码块，Prompt 一个代码块。告诉读者：把两段放进 Cursor 或任意模型的同一条消息里，再发送。

Prompt 保持原文，不翻译，不润色。要补「只返回正文」之类的调用条件，写在 Prompt 外面，别悄悄改掉被测内容。

## A/B 只讲看得见的差别

A 和 B 必须处理同一段输入。A 是裸跑或中性指令，B 加入待测 Prompt。两边各贴真实输出，别只挑一句最好看的，也别拿摘要冒充模型原话。

对照后直接点出具体词句：哪句被删了，哪个事实还在，有没有新编数字、原因或结论。「更专业」「明显提升」不算结果。

## 元数据别抢正文

来源、运行环境、日期和四道闸都放进 frontmatter。正文不再单开「运行记录」给读者复习一遍。

四道闸的意思很直白：`gate_complete` 检查问题、输入、Prompt、结果是否齐；`gate_traceable` 检查来源和摘录能否追到；`gate_safe` 检查客户名、密钥和敏感内容是否清掉；`gate_one_pass` 检查同一输入的 A/B 是否真实跑过。四项全是 `true` 才出厂。

模型名或官方输入没记录，就写 `not_recorded` 或 `rebuilt_from_ab_excerpt`。别猜。

## 收尾只留使用边界

告诉读者什么时候别用，以及结果交给谁点头。事实有没有丢、语气有没有削过头，要由人确认。涉及真实仓库、生产工作流、客户数据或长期自动化，人没批准就停。

评测只保留一张四维表：结构、约束、胡编、可执行性。其他信息都用短文或代码块，别再造表。

## 可复制空模板

复制下面整段，新建一条出厂文档。尖括号里的内容全部替换。

````md
---
title: <一句话写清解决了什么>
category: <仓库已有分类>
source: <原始 URL 或可追溯路径>
ran_on: <真实运行环境和工具>
ran_at: <YYYY-MM-DD>
model: <模型名；没记录就写 not_recorded>
input_status: <official | rebuilt_from_ab_excerpt>
excerpt_a: <A 摘录路径或运行记录>
excerpt_b: <B 摘录路径或运行记录>
gate_complete: true
gate_traceable: true
gate_safe: true
gate_one_pass: true
---
````

## 发出前读一遍

从头往下读一次。前 20 秒内必须看到原始问题、完整输入和可复制 Prompt。A/B 必须来自同一输入，差异能逐字指出，重建输入已经亮明身份，frontmatter 的四道闸全为 `true`。

读起来还像检查表，就继续删。正文应该像一页短 demo。
